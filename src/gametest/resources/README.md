# GameTest-only datapack

Fixtures that the GameTests need and that must never reach a player's world:

| File | Why |
| --- | --- |
| `data/c/tags/item/ingots/copper.json` | Plants `minecraft:brick` in `c:ingots/copper` as a stand-in for a modded ingot, so the GameTest can prove docs/SCOPE.md's M2 ladder promise — an item Forgeweave has never heard of melts because a *tag* names it, with no Forgeweave code and no Forgeweave recipe of its own. |
| `data/c/tags/item/ingots/bronze.json` | Plants `minecraft:nether_brick` in `c:ingots/bronze` (a different stand-in than copper's, so no item matches two materials at once). Originally `SteelAndTagGatedGameTests`'s fixture for tag-gating; since issue #826 migrated bronze/lead/silver/electrum to `neoforge:conditions` existence gating (whose real conditions name `mekanism`/`immersiveengineering` items neither loaded in a GameTest server), it now backs `gametest_conditional_present.json`'s `crafting_items` instead — a modid-blind condition (`item_exists` on `minecraft:diamond`) paired with the same tag-obtainability shape the real four metals still use. |
| `data/c/tags/item/dusts/gametest_dust_metal.json` | Issue #992: plants `minecraft:rabbit_foot` in `c:dusts/gametest_dust_metal`, an item no shipped melting recipe names, so `MaterialFormMeltingGameTests` can prove D-M8-6's tag-not-item rule — an item Forgeweave has never heard of melts because a *tag* names it. The material id is a fixture id rather than a real one (`steel`, say) because a file here at a shipped tag's own path **shadows** that tag instead of merging with it: both trees are folded into the one mod resource pack for the `gameTestServer` run, so `c:dusts/steel` would lose `forgeweave:steel_dust` and the shipped rows would stop melting. `GametestFixturesNotInMainResourcesTest` catches that collision. |
| `data/forgeweave/forgeweave/melting_recipe/gametest_tagged_dust.json` | Issue #992: the melting half of the pair above — the exact shape `scripts/generate_material_forms.py` emits for every real dust (`c:dusts/<id>` -&gt; a molten fluid at 144 mB), riding `forgeweave:molten_steel`. `MaterialFormsTest` pins that every shipped row has this shape; this proves a row of this shape melts a tag-only item. |
| `data/forgeweave/forgeweave/melting_recipe/gametest_above_lava.json` | A recipe at 1400, hotter than lava's 1300, so the GameTest can prove temperature gating. |
| `data/forgeweave/forgeweave/melting_recipe/gametest_above_blazing_blood.json` | Issue #903: a recipe at 1600, hotter than blazing blood's 1500, so `SmelteryFuelGameTests` can prove the ladder's rung 4 (molten magma, 1700) reaches something rung 3 cannot. Input is `minecraft:ghast_tear`, which no shipped melting recipe names. |
| `data/forgeweave/forgeweave/melting_recipe/gametest_above_molten_magma.json` | Issue #903: the same at 1800 for rung 5 (molten brimspar, 1900) against rung 4. Input `minecraft:phantom_membrane`. |
| `data/forgeweave/forgeweave/melting_recipe/gametest_above_brimspar.json` | Issue #903: the same at 2000 for rung 6 (pyrealloy, 2100) against rung 5. Input `minecraft:nether_star`. |
| `data/forgeweave/forgeweave/smeltery_fuel/gametest_super_fuel.json` | A fuel riding `minecraft:water` (inert, never a real fuel) at 5000 degrees, so `SmelteryFuelGameTests` can melt `gametest_above_lava`'s 1400-degree recipe — lava alone cannot — without waiting through the real mB/duration math a shipped superfuel would use (issue #97). |
| `data/forgeweave/forgeweave/material/gametest_conditional_present.json` | Issue #826: a `neoforge:conditions` material conditioned on `neoforge:item_exists` for `minecraft:diamond` (always true, no modded jar needed) so `ConditionalMaterialGameTests` can prove the existence-gating *positive* path — present in the material registry, the creative tab's part expansion, the guide book's material list, and craftable at the Part Builder from `c:ingots/bronze` (above). |
| `data/forgeweave/forgeweave/material/gametest_conditional_absent.json` | Issue #826: the same shape conditioned on `neoforge:mod_loaded` for a modid nothing supplies, so `ConditionalMaterialGameTests` can prove the *negative* path — absent from the material registry, the creative tab, the guide book, and unmatched by `PartBuilderRecipes.materialValue`. |
| `data/forgeweave/forgeweave/material/gametest_silver.json` | Issue #826: an unconditioned copy of `silver.json`'s stats and traits. Once silver itself was existence-gated on `immersiveengineering:ingot_silver` (absent in a GameTest server), `ArmorTraitGameTests#consecratedAgainstTheUndead` — which is testing the `consecrated` trait's behavior, not the gating mechanism — needed a still-always-present stand-in to keep wearing. |
| `data/forgeweave/forgeweave/material/gametest_electrum.json` | Issue #826: the same idea for electrum's `shocking` trait, keyed on `immersiveengineering:ingot_electrum` in the shipped material. `LauncherBranchGameTests`'s two shocking-charge tests build their bow from this fixture instead. |
| `data/forgeweave/forgeweave/melting_recipe/gametest_compat_smeltery_present.json` | Issue #873: a compat metal's melting recipe (`c:ingots/bronze` -&gt; `forgeweave:molten_bronze`, reusing the `bronze.json` tag fixture above) conditioned on the same modid-blind `item_exists minecraft:diamond` as `gametest_conditional_present.json`, so `CompatSmelteryGameTests` can prove the round-trip *positive* path -- the real `bronze_ingot.json` melting recipe cannot, since its own condition names `mekanism:ingot_bronze`, which no GameTest server has. |
| `data/forgeweave/forgeweave/casting_recipe/gametest_compat_smeltery_present.json` | Issue #873: the casting half of the pair above -- `forgeweave:molten_bronze` casts back into `minecraft:gold_ingot` (a safe, unambiguous vanilla item) at a casting table, same condition. Together the two prove a compat fluid's melting+casting recipes round-trip when their `neoforge:conditions` gate is open, without depending on any real provider mod. |
| `data/forgeweave/forgeweave/melting_recipe/gametest_track_a_diamond_tier.json` | Issue #954: a diamond-tier Track A metal's melting recipe (temperature 1400, same modid-blind `item_exists minecraft:diamond` condition as `gametest_compat_smeltery_present.json`), riding the real `forgeweave:molten_platinum` fluid. Input `minecraft:prismarine_shard`, which no shipped melting recipe names. `CompatSmelteryGameTests` proves it fails under lava (1300) and melts under blazing blood (1500). |
| `data/forgeweave/forgeweave/melting_recipe/gametest_track_a_draconium_awakened.json` | Issue #954: the same shape at awakened draconium's temperature (1800), riding `forgeweave:molten_draconium_awakened`. Input `minecraft:shulker_shell`. `CompatSmelteryGameTests` proves it fails under molten magma (1700) and melts under brimspar (1900). |
| `data/forgeweave/forgeweave/trait_definition/gametest_pack_poison.json` | Issue #832: a datapack `trait_definition` -- `effect_on_hit` at Poison **II**, one amplifier above the built-in `poisonous`'s Poison I so the effect can only have come from the pack's parameters -- for `DatapackTraitGameTests` to prove a pack-authored trait reaches a Tool-Station-assembled tool and fires. |
| `data/forgeweave/forgeweave/trait_definition/gametest_pack_absent.json` | Issue #832: the same shape gated on `neoforge:mod_loaded` for a modid nothing supplies, so `DatapackTraitGameTests` can prove a definition failing its conditions never registers (absent from the registry and from `ForgeweaveTraits.lookup`). |
| `data/forgeweave/forgeweave/modifier_recipe/gametest_socketed.json` | Issue #969: the `socketed` modifier's application recipe with a modid-blind `item_exists minecraft:diamond` condition and a vanilla reagent (`minecraft:heart_of_the_sea`, which no shipped recipe names), so `ApotheosisSocketGameTests` can apply sockets at the Tool Station. The real `socketed.json` cannot: its condition names `apotheosis`, which no GameTest server has, and its reagent is an Apotheosis item. Same `max_level` as the shipped recipe, so the slot arithmetic under test is the shipped one. |
| `data/forgeweave/forgeweave/modifier_recipe/gametest_socket_gem.json` | Issue #969: the gem-seating half of the pair above, on `minecraft:nautilus_shell`. The gem itself is stood in for by the test's own fake bridge (Apotheosis is not on the gametest classpath, per JC-B), so what this fixture proves is Forgeweave's plumbing: the station reaches the seating action, the socket component moves, and the slot is spent. |
| `data/forgeweave/forgeweave/modifier_definition/gametest_pack_chill.json` | Issue #973: a datapack `modifier_definition` -- `effect_on_hit` leaving Blindness, which no shipped modifier grants so the effect can only have come from the pack's parameters -- for `DatapackModifierGameTests` to prove a pack-authored modifier is applied at the Tool Station and fires. `CompatToggleGameTests` flips `modifierDefinitions` against the same id. |
| `data/forgeweave/forgeweave/modifier_definition/gametest_pack_absent.json` | Issue #973: the same shape gated on `neoforge:mod_loaded` for a modid nothing supplies, so `DatapackModifierGameTests` can prove a definition failing its conditions never registers (absent from the registry and from `ForgeweaveModifiers.get`). |
| `data/forgeweave/forgeweave/modifier_recipe/gametest_pack_chill.json` | Issue #973: the application half of the pair above, on `minecraft:sea_pickle` -- an item no shipped modifier recipe names. A pack-defined modifier needs a pack-defined recipe to reach a tool at all (ADR-0004 item 1 is unchanged by #973), and this fixture is that half. |
| `data/forgeweave/forgeweave/material/gametest_pack_material.json` | Issue #832: the material naming both definitions above, so the tool under test is assembled from a real material the way a player's pack would wire it, and the absent id rides the tool inertly like any unimplemented trait id. Its crafting item is `minecraft:dead_bush`, which no other material names. |
| `data/forgeweave/tags/block/smeltery/wall_addon.json` | Issue #1067: plants `minecraft:diamond_block` in `forgeweave:smeltery/wall_addon`, a tag the shipped `forgeweave:smeltery/wall` tag references with `addOptionalTag` but never ships a file for itself. `SmelteryWallTagGameTests` proves a datapack tag can admit a vanilla block as a smeltery wall. A fixture at `smeltery/wall.json`'s own path would hit the shadowing trap above and replace the shipped members instead of adding to them, so the test targets this reserved, always-empty-in-production tag instead. |

`build.gradle` puts this directory in its own `gametest` source set, wired into the mod's file list
only for the `gameTestServer` run (a second `mods` entry that folds in `sourceSets.gametest`
alongside `sourceSets.main`, set as that one run's `loadedMods` override). Every other run
(`runClient`, `runServer`, `runData`) and the published `jar` -- which packages `sourceSets.main`
only -- never see this directory (issue #927). `GametestFixturesNotInMainResourcesTest` fails the
build if that ever regresses. Adding a file here needs no extra wiring; it just needs a row above.
