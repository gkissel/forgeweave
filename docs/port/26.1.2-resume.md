## Blockers fixed in this stretch

- **`neoforge:item_exists` no longer exists in NeoForge 26.1.2** (commit `851acc557`). Its replacement is
  `{"type":"neoforge:registered","value":X}`; the `registry` field is optional and defaults to the item registry.
  - I converted 9313 conditions in 7138 JSON files, keeping each file's layout. Every rewrite was verified by parsing the JSON.
  - `generate_compat_smeltery.py` and `_compat_smeltery_data.py` now emit and read `registered`.
  - The generators were rerun: their output matches the converted JSON, apart from 6 Elementarium
    materials. That diff is the known pre-1.21.1 bow-stat drift, which was reverted and not fixed, per the coordinator.
  - Prose (Java comments, mods.toml, the gametest README) now says `registered`. `docs/SCOPE.md` keeps the historical wording.
  - Other conditions: `neoforge:mod_loaded`, `or`, `and`, `not` and `tag_empty` are unchanged; `true`
    became `always` and `false` became `never` (the repo uses neither); `forgeweave:compat_toggle` is still registered.
  - The new `src/test/.../data/ConditionTypesTest` reads the condition codec ids from NeoForgeMod's
    public `DeferredHolder` fields plus Forgeweave's `CONDITION_CODECS`, and fails on any unregistered
    type in `src/main`, `src/generated` or `src/gametest` resources. It has not run yet: if NeoForgeMod's
    static init misbehaves in a unit test, change how it reads the ids.
- **XP ledger data loss** (commit `4087cf785`). The port's `fieldOf("ledger")` would have made NeoForge
  skip every 1.21.1 ledger. `DamageXpLedger.MAP_CODEC = MapCodec.assumeMapUnsafe(CODEC)` keeps the exact 1.21.1 layout.
  - Fixture `src/test/resources/fixtures/attachment/m919_damage_xp_ledger.snbt` is captured from a real
    1.21.1 save (commit `2c70d205e`): Forgeweave 1.0.0 release jar, NeoForge 21.1.248, port 25641,
    values injected with `data merge entity` (the ledger needs a player melee hit), read out of `world/entities/r.0.0.mca`.
  - Test: `DamageXpLedgerTest#aLedgerSavedOn1_21_1LoadsAndIsWrittenBackUnchanged`. Not run yet.
- **Enchantability regression.** NeoForge 26.1.2 has no per-stack enchantment-value hook, so the fix is a backfill.
  - `item/Enchantability` has `set(stack, value)`, which writes both components; ToolAssemblyRecipes' three writes use it.
  - `Enchantability.backfill(stack)` runs at the top of `ToolItem#inventoryTick` and
    `ArmorPieceItem#inventoryTick`. When a stack has Forgeweave's component but only the item's default
    `minecraft:enchantable` (14), it copies Forgeweave's value across.
  - GameTest `EnchantabilityBackfillGameTests` (3 tests). Not run yet.
  - The leftover non-override methods `isEnchantable`, `isBookEnchantable` and
    `getEnchantmentValue(ItemStack)` on ToolItem/ArmorPieceItem are dead to vanilla, but tests still call them.
- **Datapack codecs decoding `ItemStack`** (commit `2c83d5f15`). 26.1 loads datapack registries and runs reload
  listeners before it binds item components (`ReloadableServerResources.updateComponentsAndStaticRegistryTags`).
  - `CastingRecipe.result` and `WorktableRecipe.leftovers` are now `ItemStackTemplate`. The JSON is the
    same, and `result()`/`leftovers()` still return fresh stacks.
  - The convenience constructors of RetexturedShapedRecipe, EnergizedTankRecipe and GravelFlintRecipe take `ItemStackTemplate`.
  - `GemSockets` (a component codec) still decodes `ItemStack`, but only at world load, with its raw-tag fallback.
- **Registry ids.** Clear glass and the 16 stained clear glasses got their `Properties.setId`; they were
  the first runtime crash. `tools/missing_ids.py` finds no others.
