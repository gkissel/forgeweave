# Art guide for designers

*(Versão em português: [texture-manifest.pt-BR.md](texture-manifest.pt-BR.md))*

This document is for whoever draws Forgeweave's sprites and does not know Java or the Minecraft API. It replaces the old version of this file, which stopped being accurate after issue #796 (the Forged/Legacy art split) and never explained how tools are visually assembled, what gets generated by script, or how modifier overlays work. Every rule below was checked directly against the Java code and Python scripts in the repository. Where a rule exists only as code, not as a comment or a document, I say which file enforces it, so you know where to ask if anything here goes stale.

## 1. Format and canvas

Almost every item, tool part, or mold sprite is a **16x16 RGBA PNG**. I confirmed this by opening the files: `pattern.png`, `cast.png`, `pickaxe_head.png`, and the rest of the part and tool-layer sprites are all 16x16, RGBA mode.

Size exceptions:

- **Worn armor** (the two sheets that render on the player's body, not the item icon): 64x32 RGBA, Minecraft's standard armor texture size. These are `models/armor/derived/plating_layer_1.png` and `maille_layer_1.png` (plus `_2` versions for legs, which use the leg sheet). See section 3 for how these sheets relate to the piece's item sprites.
- **Station GUI panels**: `tool_station.png` and `smeltery.png` are 256x256; `part_builder.png` and `stencil_table.png` are 176x166; `generic.png` is 64x64; `info_panel.png` and `station_icons.png` are 256x256. These panels are a layout contract: the Java code draws slots, gauges, and text at fixed pixel coordinates aligned to this art (one automated test even pins the smeltery's melt-grid geometry to the PNG). Restyle color and detail freely, but do not change a panel's dimensions or the position of any slot, window, or gauge without checking with a developer first.
- Molten metal (`molten_metal.png`, 16x320, and `molten_metal_flow.png`, 32x512) are vertical animated strips with a `.png.mcmeta` sibling. Keep both files and the frame layout if you touch them.

What the CI audit actually checks: `TextureReferenceAuditTest` (in `src/test/java/dev/gkissel/forgeweave/data/`) scans every model JSON and every texture literal in Java and confirms two things: that the referenced PNG exists on disk, and that it sits under a prefix the block atlas actually stitches (`block/`, `item/` by default, or a directory prefix declared in `assets/minecraft/atlases/blocks.json`). This test **does not check dimensions or color mode**. It will not complain if you hand in a file at the wrong size, or saved as an indexed-palette PNG instead of RGBA (I found a few older GUI PNGs, like `seared_furnace.png`, still in indexed-palette mode; RGBA is the standard to follow for new art). What actually breaks when the size is wrong are the pixel-by-pixel composite tests described in section 4 (`GreyscalePartTextureTest`, `PatternImprintCenteringTest`, `CastCompositeHoleTest`), because they compare your art, pixel by pixel, against the size the base already has. So treat 16x16 (or 64x32 for worn armor) as a hard rule even though no dedicated test shouts if you get it wrong.

Alpha: outside the tinted layers (section 2), transparency is always functional, never decorative. On smeltery blocks, the window and gauge holes are where fluid gets drawn; on gold casts (`cast_*.png`), the punched cavity is what makes a cast read as a mold. Keep those alpha shapes. Edges with partial alpha (anti-aliasing) follow the same visual judgment as the rest of the game's pixel art.

## 2. The tint rule (the most important one in this guide)

Most of Forgeweave's item art (every tool part, every layer of an assembled tool, and the two worn-armor sheets) is drawn in **pure greyscale** and colored at runtime, by code, according to the material the player built that item from. This is implemented in `ForgeweaveItemColors.java` (for items) and `ForgeweaveItemClientExtensions.java` (for worn armor, since issue #726); both apply the exact same tint.

What this means in practice for whoever draws:

- **Draw in pure grey.** Every pixel needs R = G = B. Use lightness alone (black to white) to express shading, highlights, and volume. If you put any hue into a pixel (a warmer blue in the shadow, say), that hue is destroyed the moment the engine multiplies that pixel by the material's color: pure grey is the only thing that survives the multiply predictably.
- **What the material color multiplies.** The tint is a plain per-channel multiply, the same mechanism as Minecraft's own item color: `final color = texture grey x material color / 255`, channel by channel. A pixel at lightness 255 (pure white) comes out at exactly the material's raw color. A pixel at lightness 128 comes out at half that color's intensity. A black pixel (0) stays black no matter the material. So the light-and-shadow contrast in your grey drawing is what decides the final tinted piece's contrast.
- **Where the material color comes from.** Every material has a `"color"` field in its datapack JSON, under `src/main/resources/data/forgeweave/forgeweave/material/<id>.json`. For example, `cobalt.json` has `"color": "#2882D4"`. That color is game data, not something you paint. To preview how a piece will look tinted in a given material, open your greyscale sprite in your image editor, drop that hex value into a "Multiply" blend-mode adjustment layer on top, and that is roughly what shows up in game (the exact math is the per-channel multiply described above).
- **Which sprites are NOT tinted.** Paper patterns (`pattern*.png`), gold and clay casts (`cast_*.png`, `clay_cast_*.png`), all block and GUI art, modifier reagent items (moss, reinforced plate, silky jewel, and so on), and status-effect icons (like `lacerate.png`, the scimitar's DoT) are drawn in full color and show up exactly as painted, with no runtime tint at all. Paint those normally, with whatever color you want.
- **The worn-armor special case (issue #726).** The two worn-armor texture sheets (`maille_layer_1.png`/`_2.png` and `plating_layer_1.png`/`_2.png`, 64x32 each) are also pure grey and tinted at runtime, by the same multiply, with the color of the equipped plating or maille material. Treat those sheets exactly like any other tinted layer.
- **A future system that does not apply yet.** There is a more sophisticated multi-stop color pipeline (`GreyToColorMapping`, `MaterialPartSprites`, `MaterialPartTextureProvider`, under `src/main/java/dev/gkissel/forgeweave/data/sprite/`) that generates pre-tinted versions of two proof-of-concept sprites per material at datagen time. It writes its output to a staging folder (`textures/staging/part/`) that no live model reads today; it is groundwork for a future rewrite (M9) that does not touch anything currently shipping. Ignore that system for now: what applies today, for everything you draw, is the plain multiply described above.

## 3. Anatomy of every assembled item

Every tool and every armor piece is assembled from parts, and each part draws a separate image layer when the item is held or displayed. Layers stack back to front in a fixed drawing order (handle always behind, then heads, then the extra piece like a guard or a binding), defined in `ToolArt.java`, and that order **is not necessarily the order parts go into the Tool Station**. For example, the vein hammer's parts go into the station as head, handle, binding, head (issue #157), but it draws on screen as handle behind, then both heads, then the binding in front, or the handle would render on top of the head.

Each layer has a role name (`handle`, `head`, `binding`, `limb`, `string`, `body`, `shaft`, `fletching`, `plating`, `maille`), not the tool's slot name. When a tool has two parts of the same role (two heads, two handles), the second one onward gets a numeric suffix: `head`, `head2`, `head3`. Each layer's file is `<tool>_<layer name>.png`, saved under `textures/derived/tools/`, except where I marked fully original art below.

**Two things worth knowing, surprising enough that I am flagging them here:**

1. **Heavy armor's third slot renders nothing today.** The four heavy armor pieces (`heavy_helmet`, `heavy_chestplate`, `heavy_leggings`, `heavy_boots`, issue #735) assemble from three parts: plating, maille, and an extra `large_plate` that feeds into stats and material traits. But `ToolArt.layerSlots` filters any armor item's layer list down to just `MAILLE` and `PLATING`, so that third part has no visual layer at all: a heavy piece renders with the exact same two files as the normal piece in that family (`helmet_maille.png`/`helmet_plating.png`, and so on), and the `large_plate` stays invisible on the model. The code itself flags this as provisional ("armor draws only its maille and plating (...) drop this filter when it gets one"), waiting on the designer art M9 was supposed to bring. If you draw a third layer for the heavy variant, it will not show up until a developer removes that filter and wires the new file in somewhere.
2. **A part's standalone item icon and its assembled-tool layer are not always the same drawing.** Every part has its own icon when it sits loose in the inventory or comes out of the Part Builder, at `textures/derived/item/<part id>.png` (for example `tool_binding.png`). That is a **different** file from `textures/derived/tools/<tool>_<layer>.png`, even when the names look like they line up. For some parts (the pickaxe head, the hammer head) the two files are pixel-for-pixel identical today. For others (the broadsword's wide guard, the pickaxe's binding) they are different, because the standalone icon is centered like an ordinary item while the tool layer needs to line up with the other layers stacked above or below it. Before drawing a new part, check the existing pair (standalone icon vs. tool layer) for another part of the same role to see whether you need one drawing or two differently-framed ones.

## 4. What you draw by hand versus what gets generated

Most of Forgeweave's item art is not 100% hand-drawn: it is a base sprite you draw, plus a Python script under `scripts/` that composites the derived variants from it (paper pattern, gold cast, clay cast, broken art). That means, most of the time, you draw **one part** and run scripts, rather than drawing four or five derived files one by one.

The four scripts you run every time you change a part's or a tool head's art:

- **`scripts/generate_pattern_textures.py`**: reads the blank paper pattern (`pattern.png`) and each part's greyscale silhouette, and writes `pattern_<part>.png`, a paper pattern with that part's silhouette etched into it (darker at the edges, slightly lighter in the interior). Each part has its own (x, y) offset in the script, so the etched imprint lands centered on the pattern even when the part's own art is not centered on its 16x16 canvas (issue #337 documents this problem). If you redraw a part and its art shifts position on the canvas, you may need to adjust that offset too; ask a developer if you are not sure.
- **`scripts/generate_cast_textures.py`**: reads the blank gold cast (`cast.png`) and the same greyscale silhouette for each part, and writes `cast_<part>.png`: the gold cast with a hole punched through it in the part's silhouette and a darkened bevel around the hole.
- **`scripts/generate_clay_cast_textures.py`**: reads every existing `cast_<part>.png` and writes `clay_<same name>.png`, applying the same mauve color multiply the original Tinkers' Construct uses for its clay cast (upstream never had a dedicated clay sprite; it reused the gold cast model with a runtime color multiply that Forgeweave does not have, so this script bakes that multiply once and writes the result).
- **`scripts/derive_broken_art.py`**: generates broken-tool art. For most tools, it copies a "broken" file straight from Tinkers' Construct 1.12 itself. For the five tools with no 1.12 counterpart (dagger, katana, scimitar, vein hammer, warmace, plus the shuriken), there is no reference art, so the script applies an algorithmic transform (`chip()`) to the tool's own head: it projects the opaque pixels onto the shape's principal axis and erases the outermost 15% at each end, visually mimicking a chip. Only the `head` (or the hammer's `handle`, or the bows' `string`) ever breaks visually; which layer breaks on which tool lives in `ToolArt.BROKEN_LAYERS`.

Two exceptions that fall outside this automation, which I found while reading the scripts:

- **The large plate** (used as an extra head on several Tool Forge-tier tools and as part of heavy armor) has a hand-drawn paper pattern and a hand-drawn gold cast from the original Tinkers' Construct (the creeper face), instead of a script-composited one. `generate_pattern_textures.py` and `generate_cast_textures.py` simply copy those two files, byte for byte, from the 1.12 clone, instead of compositing from the part's silhouette. If `large_plate.png` changes shape, those two hand-drawn files do **not** follow along automatically; they would need to be redrawn separately.
- **The katana's handle and binding** (`textures/tools/katana_handle.png` and `katana_binding.png`, note the `tools/` folder without `derived/`) are 100% original Forgeweave art, not derived from any outside source. The katana's head (`katana_head.png`) comes from Spartan Weaponry (see section 8) and lives under `derived/tools/` like any other derived layer, but those other two layers deliberately sit outside the `derived/` tree, because Spartan Weaponry has no katana guard or handle to donate (its art fuses the guard into three pixels of the blade body and draws the handle in a fixed color with no tint at all).

If you are adding a brand-new tool or piece (not just replacing an existing one's art), these scripts generally cover the case automatically as long as you drop the part's silhouette at the right path with the right name. See section 7 for the full checklist.

## 5. Modifier overlays

When a player applies a modifier with a visual effect (sharpness, diamond, emerald, reinforced, luck, fiery, shulking, and others) to a tool, the game draws an extra layer on top of the assembled item: the modifier overlay. This lives in `ModifierArt.java`, the modifier-side sibling of `ToolArt.java`. Unlike part layers, an overlay is **never tinted**: it is drawn in full color and shows up exactly as painted.

Rules I confirmed in the code:

- The set of modifiers that get an overlay is `ModifierArt.OVERLAY_MODIFIERS`. A modifier outside that list (Forgeweave's own originals: `searing`, `magnetic_pull`, `aquadynamic`, `resonant`, `far_reach`, `extra_slot`, `wind_burst`, plus the generated embossments) draws nothing on purpose. Tinkers' Construct 1.12 itself also has modifiers with no overlay (its own creative modifier, for example), so this is not a gap, it is intentional.
- An overlay's file lives at `textures/derived/tools/mods/<tool>_<modifier>.png`.
- Armor pieces **never** get a modifier overlay: 1.12 had no armor to have that art in the first place, and the defense modifier family armor uses today shows through the worn layers, not an item overlay.
- The three bows (`shortbow`, `longbow`, `crossbow`) have per-draw-stage overlay variants (`_draw1`, `_draw2`, `_draw3`), but not every tool/modifier pair has all three. `ModifierArt.STAGED_OVERLAYS` lists exactly which combinations have staged art; anything outside that list keeps the undrawn overlay at every stage.
- A (tool, modifier) pair can have no overlay for three reasons, all documented in `ModifierArt.NO_UPSTREAM_ART`: the modifier does not apply to that tool category (luck refuses launchers, for example), or the original Tinkers' Construct simply never drew that pair (a gap in the original game, not in Forgeweave).

**How to add art for a modifier that has none today:** this needs a code change, not just a new file. Draw the file at `textures/derived/tools/mods/<tool>_<modifier>.png` (follow the same 16x16, full-color framing as the files already in that folder) and ask a developer to add the modifier's `ResourceLocation` to `ModifierArt.OVERLAY_MODIFIERS`. Without that second step, the game never loads the file, no matter how correct its name is: an automated test (`ModifierArtTest`) actually fails on purpose if a file sits in that folder that no (tool, modifier) pair resolves to, so an orphaned file does not slip through unnoticed.

## 6. Forged and Legacy (issue #796)

Since issue #796, Forgeweave ships two art sets:

- **Forged**: new original art, drawn by the maintainer's designer. It is the default set, what every player sees without doing anything. It lives at the normal paths, under `src/main/resources/assets/forgeweave/textures/...`.
- **Legacy**: the art Forgeweave used before #796 (mostly derived from Tinkers' Construct 1.12, plus a handful of files from Spartan Weaponry). It stays available, but as a built-in resource pack, off by default, that a player enables manually under Options > Resource Packs if they want the old look back. That pack lives at `src/main/resources/resourcepacks/legacy/assets/forgeweave/...`, using the exact same relative paths as the default tree, because that is how a Minecraft resource pack overrides a texture: same relative path, the enabled pack wins.

That means a file under `textures/derived/...` no longer tells you, on its own, whether the pixels currently shipping are derived from upstream. As each Forged sprite gets added, it replaces the file at the default path, and the old derived file it replaced moves to the same relative path inside the Legacy pack (its `NOTICE.md` row moves with it, see section 8). The `derived/` folder name stays the same for every file either way, so today it means "this is where a licensing note would go if the pixels currently shipping needed one," not "these pixels are derived."

**The exact steps to add the next Forged sprite**, pulled from `scripts/sprite_sets.py` and the flow the four generator scripts already follow:

1. Drop the new file at its usual default path (`assets/forgeweave/textures/...`), replacing what was there.
2. Copy the file it replaced to the same relative path inside the Legacy pack (`resourcepacks/legacy/assets/forgeweave/textures/...`).
3. Rerun the four generator scripts: `generate_pattern_textures.py`, `generate_cast_textures.py`, `generate_clay_cast_textures.py`, and `derive_broken_art.py`.
4. A developer checks which `NOTICE.md` rows need to move to the Legacy pack (and, if the file came from Spartan Weaponry, updates the modification notice in `licenses/APACHE-2.0-SpartanWeaponry.txt`).

Each of the four scripts in step 3 already does both passes on its own, with no code change needed: it writes the Forged output normally and, in a second pass, recomposes that same output from the Legacy set's own files (using whatever override the Legacy pack already ships, falling back to the shared Forged/default file otherwise), and only actually writes a file into the Legacy pack if the result is **different**, byte for byte, from what the Forged pass just wrote. This exists so the Legacy pack never accumulates copies identical to Forged (a test, `LegacyResourcePackTest`, fails if that happens) and never leaves behind an orphan file that overrides nothing real.

## 7. Delivery checklist

What to hand over for a new or replaced sprite, and the commands a developer runs to get it live:

**You hand over:**

1. The PNG in RGBA, at the right size (16x16 for the vast majority of item and layer sprites, 64x32 for a worn-armor sheet). See section 1.
2. Pure grey (R=G=B on every pixel) if the file is a part, an assembled tool layer, or a worn-armor sheet (anything section 2 marks as tinted). Full color if it is a pattern, a gold or clay cast, a modifier overlay, or any block/GUI/reagent art.
3. The right file name in the right place. For a new part: `textures/derived/item/<part id>.png` (the standalone icon) and, if the part goes into a tool as a layer, `textures/derived/tools/<tool>_<role>.png` (the assembled layer, see section 3 for the role's name and whether it might need a different framing).
4. If you are replacing the art of a part that already has a derived pattern, cast, or broken variant, you do not need to draw those yourself: they are generated by the scripts in section 4.

**A developer runs, once your file is in place:**

```
python3 scripts/generate_pattern_textures.py
python3 scripts/generate_cast_textures.py
python3 scripts/generate_clay_cast_textures.py
python3 scripts/derive_broken_art.py
./gradlew runData
./gradlew test
```

`./gradlew runData` regenerates any datagen output that depends on art (item models, for instance), and that generated output needs to be committed along with everything else: a CI check blocks the build if datagen goes stale. `./gradlew test` runs the full suite, including the tests that compare your new art pixel by pixel against what the scripts generated (`GreyscalePartTextureTest`, `PatternImprintCenteringTest`, `CastCompositeHoleTest`) and the ones that confirm every texture path exists and is in the right place (`TextureReferenceAuditTest`, `ModifierArtTest`, `LegacyResourcePackTest`). If one of those tests fails after your delivery, it usually means one of the scripts above needs to run again, or a composite offset (issue #337, section 4) needs adjusting.

## 8. Licensing, in one paragraph

Fully original Forgeweave art (most of the Forged set, plus some older art like the katana's handle and binding layers) needs no `NOTICE.md` row at all: it is yours, no obligation attached. Art derived from upstream (most of today's Legacy set, plus any Forged file that has not been replaced yet) carries one row per file in `NOTICE.md`, at the repository root, naming the source license (most are MIT, from Tinkers' Construct; a handful, like the katana's and scimitar's blades, are Apache-2.0, from Spartan Weaponry, which also needs an extra note in `licenses/APACHE-2.0-SpartanWeaponry.txt`). When a Forged sprite replaces a derived file at the default path (section 6), that file's `NOTICE.md` row does not disappear, it moves to the Legacy pack's path, because that is where the derived pixels actually still live. As a designer, you never need to read or copy anything from Tinkers' Construct, Mantle, or Spartan Weaponry to draw Forged art: moving and annotating the NOTICE rows is the job of whoever reviews your file before it gets committed, not yours.

## Worked example: from drawing to the game

Say you are redrawing the pickaxe head (`pickaxe_head`), the simplest part in the game. Here is the full path:

1. You open `src/main/resources/assets/forgeweave/textures/derived/item/pickaxe_head.png` (16x16, RGBA) and redraw the silhouette in pure grey, keeping whatever light-and-shadow contrast you want (remember section 2: lightness is what decides the final tinted contrast).
2. You hand that file to a developer, flagging whether the silhouette moved position within the 16x16 canvas (that matters for the pattern's offset, section 4).
3. The developer copies that same file (or a reframed version, if the position changed) to `src/main/resources/assets/forgeweave/textures/derived/tools/pickaxe_head.png`, the assembled-tool layer, because today the two are pixel-for-pixel identical for the pickaxe (which is not always the case, see section 3).
4. The developer copies the old `pickaxe_head.png` (whatever was shipping before your change) to the same relative path inside `resourcepacks/legacy/...`, preserving the old look as Legacy.
5. They run `scripts/generate_pattern_textures.py` and `scripts/generate_cast_textures.py`, which recompose `pattern_pickaxe_head.png` and `cast_pickaxe_head.png` from the new silhouette (and write the matching Legacy versions, since the old pattern and cast silhouette is now different from the new one).
6. They run `scripts/generate_clay_cast_textures.py`, which recomposes `clay_cast_pickaxe_head.png` from the `cast_pickaxe_head.png` that just changed.
7. `pickaxe_head` is one of the heads with broken art ported straight from Tinkers' Construct 1.12 (not one of the five that use the `chip()` transform), so `derive_broken_art.py` does not need to run again for it: that head's broken art is an independent file, not derived from the intact one.
8. `./gradlew runData` regenerates the generated models that reference these textures, and `./gradlew test` confirms the new pickaxe matches what the scripts generated and that no texture path is left orphaned.
9. In game: the assembled pickaxe with a cobalt head shows your new silhouette multiplied by the material's `#2882D4` blue; the paper pattern and gold cast for the pickaxe head at the Part Builder show the new silhouette etched and punched; and anyone with the Legacy resource pack enabled keeps seeing the old pickaxe head, the way it was before your change.
