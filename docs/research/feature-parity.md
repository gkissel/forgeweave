# Feature parity: Forgeweave vs Tinkers' Construct 2 (1.12.2) vs Tinkers' Construct 3 (1.20.1)

## Method note

Three sources were read directly for this survey, not recalled from training data:

- **Forgeweave**: `master` at commit `9f5cf17` (`src/main/java/dev/gkissel/forgeweave/**`, `src/main/resources/data/forgeweave/**`), `docs/SCOPE.md`, `CONTEXT.md`, `docs/adr/000{1,2,3}-*.md`, `NOTICE.md`, and all 30 GitHub issues in `gkissel/forgeweave` (`gh issue list --state all`).
- **Tinkers' Construct 2**: local clone `~/development/minecraft/references/tinkers-1.12`, branch `1.12`, pinned commit `c01173c0408352c50a2e8c5017552323ce42f5b4` (matches CLAUDE.md's pin). Package root `slimeknights/tconstruct/{tools,smeltery,gadgets,world,library,plugin}`.
- **Tinkers' Construct 3**: local clone `~/development/minecraft/references/tinkers-1.20`, branch `1.20.1`, pinned commit `de26560d26c15edf93e6078520202d1c0518394e` (matches CLAUDE.md's pin). Package root `slimeknights/tconstruct/{tools,tables,smeltery,gadgets,world,library,plugin}`.

Both clones were walked by directory listing and targeted `grep` against their registration classes (`TinkerTools`, `TinkerMaterials`, `TinkerModifiers`, `TinkerTraits`, `TinkerGadgets`, `TinkerWorld`, `TinkerSmeltery`, `plugin/jei/*`) rather than read wholesale; every claim below cites the class or file that backs it. Where a claim could not be verified from code in the time available, it is marked **unverified** rather than asserted.

Status values in the table:

- **Have** — merged on Forgeweave `master`; issue/PR number cited.
- **Planned** — named in a specific milestone (`docs/SCOPE.md` M2–M9) or open issue; cited.
- **Not planned** — explicitly excluded, either as an M1 non-goal or by scope policy; cited.
- **Unknown/undecided** — no mention in `SCOPE.md`, `CONTEXT.md`, or any issue. These feed the "Unknowns" section.

## Features Forgeweave has that neither upstream has

- **Datapack-first materials from the very first playable milestone.** Both TiC2 (static Java fields) and TiC3 (JSON, but arrived only in the TiC2→TiC3 rewrite, years into that project's life) required either a code change or a major-version rewrite to make materials data-driven. Forgeweave's `Material` is a NeoForge datapack registry from M1 issue #7 onward — `ADR-0002` makes this a day-one architectural commitment, not a later migration. Verified in `material/Material.java`'s codec and `data/forgeweave/forgeweave/material/*.json`.
- **A single shared side-inventory/info-panel implementation across all three M1 stations.** PR #63 explicitly extracted `SideInventory`/`SideInventorySlots`/`SideInventoryPanel` and reused `InfoPanel` so Crafting Station, Part Builder, and Tool Station all get attached-chest support and stat panels from one code path rather than three near-duplicates. Whether TiC2/TiC3 share this degree of code across their equivalent stations was not confirmed either way (their GUI classes are more numerous and per-station, e.g. TiC2's `GuiPartBuilder`/`GuiToolStation`/`GuiCraftingStation` each have distinct implementations) — this is a plausible but **not fully verified** Forgeweave-only trait, listed here with that caveat rather than asserted outright.
- **Smeltery melting/casting scoped to work with *any* mod's ores via vanilla/NeoForge `c:` (common) tags, decided before the smeltery itself is built.** `docs/SCOPE.md`'s M2 line is explicit: "Melts/casts any mod's ores and ingots via standard `c:` tags, so modded metals (Mekanism, Create, Thermal, …) work without per-mod code." TiC2 required per-mod compat modules or addons for this; TiC3's compat story is JSON-material-based but not represented as a tag-driven day-one guarantee in the code surveyed. This is a **planned**, not yet shipped, Forgeweave differentiator — flagged here because the *design decision* already exists in SCOPE.md even though M2 hasn't landed.

## Notable divergences (deliberate, not gaps)

- **No numeric harvest-level system.** `CONTEXT.md` invariant: "Harvest capability uses vanilla 1.21 tool-tier tags (`needs_iron_tool`, …), never a custom numeric harvest-level system." Both TiC2 and TiC3 use Tinkers' own harvest-level integer scale tied to material stats. Forgeweave's `Material.incorrectForTool` is a `TagKey<Block>`, not a level int (`material/Material.java`).
- **"Tinkers"/"TiC" vocabulary is deliberately avoided everywhere except provenance docs** (`CONTEXT.md`: "Avoided terminology"). All Forgeweave identifiers, block names, and player text are independent even where the mechanic is a direct port — e.g. "Tool Station" instead of TiC3's renamed "Tinker Station," "Broken" instead of upstream's terminology for 0-durability tools.
- **Traits stay a distinct Java mechanism from Modifiers, matching TiC2's split rather than TiC3's unification.** TiC3 folded traits into Modifiers as one subcategory (`tools/modifiers/traits/`); Forgeweave's `CONTEXT.md` explicitly keeps them separate ("Modifier... distinct from Trait") and `trait/ForgeweaveTraits`'s javadoc treats trait behavior as intentionally not-a-registry, unlike TiC3's JSON-driven `ModifierManager`. This is a considered choice per the M1/M2 milestone split, not an oversight.
- **Per-milestone source policy (Derive vs Inspire) is recorded explicitly**, unlike either upstream project which is simply itself. `docs/SCOPE.md`'s "Milestone sources" table names exactly which addons are MIT-derivation-eligible (Tinkers' Tool Leveling, Tinker's JEI) versus inspiration-only (TAIGA, PlusTiC, Construct's Armory, Moar Tinkers), and explicitly excludes Ceramics and Tinkers' Complement from any role.
- **Tools are never destroyed at 0 durability, only Broken, with no config to change that.** This matches TiC2/TiC3 conceptually (both have a "broken" tool state) but Forgeweave states it as a hard invariant (`CONTEXT.md`) rather than a config-toggleable behavior.

## Unknowns needing a maintainer decision

- **World generation has no milestone at all.** Neither slime islands (TiC2 `world/worldgen/*`, TiC3's expanded earth/sky/ender slime biomes) nor cobalt/ardite ore generation appear anywhere in `docs/SCOPE.md`'s M1–M9 ladder, as either a planned feature or an explicit non-goal. This is the single largest unaddressed feature area in either upstream and needs an explicit scope decision (own milestone, folded into M2/M6, or a written non-goal).
- **Guidebook has no milestone beyond its M1 non-goal.** `docs/SCOPE.md` excludes it from M1 but never revisits it in M2–M9. Both upstreams treat an in-game book as core (TiC2 one book; TiC3 six books across two mod-integration tiers). Decide whether Forgeweave ever ships one, and if so, at which milestone.
- **The mid/heavy tool roster is unnamed.** M3's issue (#24) and `docs/SCOPE.md` name only two *specific* new shapes (a katana-like weapon, an energy-consuming ranged tool, both PlusTiC-inspired) but never state whether TiC2's hammer, excavator, lumber axe, mattock, scythe, kama, or its melee family (broadsword, rapier, longsword, cleaver, battleaxe) are in or out. Same for TiC2's bow/crossbow/shuriken ranged line. This needs to be itemized before M3 planning, not discovered mid-implementation.
- **Gadgets beyond slingshot and slime boots are unnamed.** M5's issue (#26) names only those two. TiC2/TiC3 both ship additional gadgets (EFLN/throwables, piggyback pack, drying rack, item rack, wooden hopper) with no stated Forgeweave position, in or out.
- **Whether M2 Modifiers will be JSON/datapack-driven (TiC3-style) or Java-registered (Forgeweave's own Trait-style precedent) is undecided.** `ADR-0002` commits Traits to Java-registration-only; nothing in SCOPE.md or the M2 issue states whether Modifiers get the same treatment or follow TiC3's fully data-driven `ModifierManager` pattern. This materially affects the M6 "50–70 materials / 30–45 traits" sizing target's addon story and should be decided at M2 planning, per SCOPE.md's own "per-milestone gate template" requirement.
- **EMI vs. JEI-only is already flagged as open in `docs/SCOPE.md`** ("revisit at M8") — carried forward here since it's a genuine unresolved item, not new.
- **Apotheosis integration shape is already flagged as open in `docs/SCOPE.md`** ("vanilla-enchanting flag interplay vs. gem sockets as Modifiers, revisit at M8") — carried forward, not new.
- **TiC3's Pattern/Stencil-Table flow was not fully traced.** No `StencilTable`-equivalent block class was found in TiC3's `tables/block`, and its Pattern Chest appears consolidated differently (a generic `TinkersChestBlock` plus a dedicated `CastChestBlockEntity`, not a 1:1 Pattern/Part split). This doesn't block Forgeweave's already-shipped M1 stencil/chest design (which derives from **TiC2**, per `docs/SCOPE.md`'s explicit "feature target: 1.12" policy), but a maintainer revisiting station UX later should know TiC3 changed this flow rather than assume it's identical to TiC2's.
